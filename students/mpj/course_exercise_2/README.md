# N-Body Simulation: Barnes-Hut Algorithm (Fortran)

This project implements a **3D N-body gravitational simulation** using the **Barnes-Hut (Octree) algorithm**, written in **Fortran**. 

The simulation supports three execution modes:
- **Serial**
- **OpenMP** (shared-memory parallelism)
- **MPI** (distributed-memory parallelism)

By default, the simulation uses a galactic disk configuration where particles rotate around a massive central object (e.g., a Black Hole).

---

## Project Structure

The project is organized into specific directories for different physical scenarios:

### Root Directory
- `geometry.f90`: module defining `vector3d` and `point3d` types, and charging mathematical operations between points and vectors.  
- `particle.f90`: module defining the `particle3d` type, specified by a mass and the position and velocity components.

- `tree_serial.f90`: Serial implementation of the Barnes-Hut algorithm.
- `tree_openmp.f90`: Parallel implementation using OpenMP for shared-memory systems.
- `tree_MPI.f90`: Parallel implementation using MPI for distributed-memory systems.
- `input_rotation.f90`: Program to generate the initial galactic disk rotation conditions. It creates a file called `input_rotation.dat`, which will be the input for the integration scripts.

- `Original.f90`: This is the original code for the Barnes–Hut algorithm extracted from Angel de Vicente's TAP book, without any modifications I have after made.

- `animation.py`: Python script for 3D visualization of the results, giving a gif.
- `Makefile`: Automates compilation and execution. It generates one executable and output file per execution mode, producing the corresponding output files:
  - `output.dat`
  - `output_openmp.dat`
  - `output_mpi.dat`
In the output files, each line represents the complete temporal system state in the format:  time p1x p1y p1z p2x p2y p2z ... pnx pny pnz


The repository has also two main specialized directories, each containing the necessary configuration and generation scripts to define the physical scenario of the simulation:

- `rotation/` (Default Scenario): Contains the source code and input generators to simulate a galactic disk. It also contains a python script for obtaining the gif of the simulation.

- `spherical_collapse/`: Contains the scripts and parameters required to simulate a "cold" gravitational collapse. In this mode, particles are distributed in a spherical shell with zero initial velocity, falling radially towards the center of mass.

To switch the physical scenario, simply migrate the contents of the desired subdirectory to the project root.

Finally, there is another folder with the gifs of temporal evolution:

- `animations/`: Dedicated directory for visual outputs. It stores high-resolution .gif files representing the system's temporal evolution. These animations are generated by the Python scripts and are automatically saved here upon execution (ensure the output path in your .py files is correctly configured).


## Initial configuration

The simulation parameters are defined during the pre-processing stage. To modify the duration, precision, or scale of the simulation, you must edit the following values within the `input_rotation.f90` (or `input_spherical.f90`) generator before execution:

- dt: Integration time step
- dt_out: Frequency of data output to disk
- t_end: Total duration of the simulation
- n: Total number of particles
- mass: Total system mass (distributed as $M/N$ per particle).


## Compilation

To compile the program, you can run specific versions or use the automated execution targets in the Makefile.

- Running using Makefile:
To compile the program
```bash
make
```

```bash
make run_all
```

To clean up the generated object (.o), module (.mod) files, inputs and outputs, run:
```bash
make clean
```

- Running without Makefile

To run the OpenMP version (ensure OMP_NUM_THREADS is set) use:
```bash
gfortran -fopenmp geometry.f90 particle.f90 tree_openmp.f90 -o tree_omp
OMP_NUM_THREADS=8 ./tree_omp < input_rotation.dat
```
8 is the number of threads used at runtime. You can modify it as you desire.

The OpenMP-enabled source file can also be compiled without the -fopenmp flag. In this case, all OpenMP directives are ignored and the program executes in serial mode, behaving identically to the serial version.

```bash
gfortran geometry.f90 particle.f90 tree_openmp.f90 -o tree_omp_serial
./tree_omp_serial < input_rotation.dat
```


To run the MPI version with 4 processes use:
```bash
mpif90 geometry.f90 particle.f90 tree_MPI.f90 -o tree_MPI
mpirun -np 4 ./tree_MPI < input.dat
```

## Code Overview

The code implements a three-dimensional gravitational **N-body simulation** based on the **Barnes–Hut algorithm**, which reduces the computational complexity of force evaluation from \(O(N^2)\) to approximately \(O(N \log N)\).

At each simulation time step, the following operations are performed:

1. **Tree Construction**  
   An octree data structure is built by recursively subdividing the simulation domain. Particles are inserted into the tree, and each node stores aggregated information such as total mass and center of mass.

2. **Force Computation**  
   For each particle, gravitational forces are computed by traversing the tree. Depending on the opening-angle criterion, distant particle groups are approximated by their center of mass, while nearby particles are treated individually.

3. **Time Integration**  
   Particle positions and velocities are updated using a time-stepping integration scheme based on the computed forces.

4. **Output Generation**  
   The system state is written to an output file at each time step, storing the simulation time and the spatial coordinates of all particles.

The code is modular, separating geometric definitions, particle data structures, and tree-based force evaluation.

After running the Makefile, the program prints three execution-time summaries corresponding to the **Serial**, **OpenMP**, and **MPI** implementations. Each summary reports the total execution time as well as a breakdown of the time spent in the main computational stages of the simulation.

The reported timings include:
- **Octree reconstruction**, corresponding to the construction of the Barnes–Hut tree at each time step
- **Gravitational force calculations**, which dominate the computational cost
- **Integration and output**, including time integration and data writing

The program also prints, for each stage, the percentage of the total execution time, which helps identify which parts of the code benefit most from parallelization.

# Discussion of the results

1. Gravity Calculations
This phase benefits the most from parallelization. In the OpenMP version, the time is nearly cut in half (from 43.7s to 24.5s). Since force calculations for each particle are independent, the workload is distributed very efficiently across CPU threads.

2. The Cost of Tree Reconstruction
We observe that in both OpenMP and MPI, the reconstruction time increases compared to the serial version (Serial: 11.6s, MPI: 19.7s). This happens because Octree construction is an inherently sequential task in this implementation. In the MPI case, every process must rebuild the entire tree locally after receiving position updates from all other ranks, adding significant memory management and computational redundancy.

3. MPI vs. OpenMP 
OpenMP achieves the best overall time due to the low latency of shared memory. MPI shows a slight increase in total time compared to OpenMP. This is expected in systems with a relatively small number of particles/processes, as the time spent on network communication to sync positions and tree duplication offsets some of the gains made during the parallel force calculations.

4. Efficiency and Scalability
Despite using 8 threads for OpenMP and 4 processes for MPI, the speedup is not linear. The Barnes-Hut algorithm has a complexity of $O(N \log N)$. According to Amdahl's Law, the sequential nature of the tree construction acts as a bottleneck; no matter how much we accelerate the gravity calculations, the total gain is limited by the non-parallelized sections of the code.

In the test involving a larger number of particles (50k to 100k), we observed that the time percentages for each phase of the algorithm remain virtually unchanged. Furthermore, the expected scaling law is satisfied. When increasing the number of particles from 50,000 to 100,000, the theoretical time increase factor is:$$\frac{100,000 \cdot \log(100,000)}{50,000 \cdot \log(50,000)} \approx 2.12 .$$ Comparing the three approaches (Serial, OpenMP, and MPI), our experimental results align perfectly with this factor.



# SUMMARY ABOUT RESULTS

Crucially, analyzing the execution breakdown reveals the distinct impact of parallelization. In the serial version, gravity calculations dominate (~77% of runtime). However, in the OpenMP and MPI versions, the relative weight of the Octree reconstruction increases significantly (jumping from ~16% to over 30%). This confirms that while the $N^2$-like force calculation is highly parallelizable, the tree structure management incurs significant overhead (synchronization in OpenMP and communication in MPI), preventing linear scaling. Besides, we have checked that the time scaling with the number of particles in this algorithm goes with $O(N \log N)$.

Attempts to parallelize the tree construction were discarded due to its recursive nature. The need for complex synchronization to manage the dynamic node creation introduced excessive overhead that degraded performance. Thus, despite the idle threads and cache penalties increasing the construction time in parallel modes, keeping this phase serial proved more robust than a poorly scaling parallel implementation.
